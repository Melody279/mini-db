# 数据模型 v0（9 张表）

> 状态：M0 冻结草案。字段改名或加列须在周五走查会上提出并记入开发日志。
> 约定：**全部定长**（varchar 一律按 char(n) 计），记录 = 定长字节串，RID 即可唯一定位。
> 列偏移由 `Catalog::CreateTable` 按列顺序累加计算，`record_size` 同时写入 catalog.dat。

## 1. 表清单

| # | 表 | 作用 | 主键 | 估计记录字节 |
|---|---|---|---|---|
| 1 | `accounts` | 三角色统一登录入口 | uid | 4+4+32+64+4+8 = 116 |
| 2 | `passengers` | 乘客档案 | pid | 4+4+11+32+8 = 59 |
| 3 | `drivers` | 司机档案、在线状态、审核状态 | did | 4+4+32+11+20+4+4+8 = 87 |
| 4 | `vehicles` | 车辆档案与运营状态 | vid | 4+4+8+16+4+4 = 40 |
| 5 | `price_rules` | 计价规则（按车型、生效时间） | rid | 4+8+8+8+8+4+8 = 48 |
| 6 | `addresses` | 乘客常用地址 | aid | 4+4+16+4+4+64 = 96 |
| 7 | `orders` | 订单主表（含状态与时间节点） | oid | 216（见 §3） |
| 8 | `order_events` | 状态流转事件（时间轴 + 审计） | eid | 8+8+4+4+8+4 = 36 |
| 9 | `reviews` | 乘客评价（选做但先建表） | rvid | 8+8+4+4+4+128+8 = 164 |

## 2. 列定义

### accounts
| 列 | 类型 | 说明 |
|---|---|---|
| uid | int32 | 主键 |
| role | int32 | 1 管理员 / 2 司机 / 3 乘客 |
| login_name | char(32) | 唯一 |
| pwd_hash | char(64) | 课程作业不做真实加密，存摘要即可（文档中说明） |
| ref_id | int32 | 指向 did / pid，管理员为 0 |
| created_at | timestamp | 注册时间 |

### passengers
| 列 | 类型 | 说明 |
|---|---|---|
| pid | int32 | 主键 |
| uid | int32 | 关联 accounts |
| phone | char(11) | 唯一 |
| name | char(32) | |
| created_at | timestamp | |

### drivers
| 列 | 类型 | 说明 |
|---|---|---|
| did | int32 | 主键 |
| uid | int32 | 关联 accounts |
| name | char(32) | |
| phone | char(11) | 唯一 |

### vehicles
| 列 | 类型 | 说明 |
|---|---|---|
| vid | int32 | 主键 |
| did | int32 | 所属司机 |

### price_rules
| 列 | 类型 | 说明 |
|---|---|---|
| rid | int32 | 主键 |
| car_type | char(8) | 车型 |

### addresses
| 列 | 类型 | 说明 |
|---|---|---|

### orders（核心表）
| 列 | 类型 | 说明 |
|---|---|---|
| oid | int64 | 主键（全局自增，同时作为 COUNT(DISTINCT) 的去重口径） |
| pid | int32 | 乘客 |
| did | int32 | 司机，未接单时 0 |
| vid | int32 | 车辆，未接单时 0 |
| car_type | char(8) | 下单时选择的车型 |
| from_addr | char(64) | 上车点 |
| to_addr | char(64) | 下车点 |
| state | int32 | 1 待接单 / 2 已接单 / 3 司机已到达 / 4 行程中 / 5 已完成 / 6 已取消 |
| created_at | timestamp | 下单时间 |
| accepted_at | timestamp | 接单时间，未发生为 0 |
| arrived_at | timestamp | 到达时间，未发生为 0 |
| started_at | timestamp | 开始行程，未发生为 0 |
| finished_at | timestamp | 结束行程，未发生为 0 |
| distance_m | int32 | 里程（米） |
| duration_s | int32 | 时长（秒） |
| fare | money | 车费（分），未完成为 0 |

record_size = 8+4+4+4+8+64+64+4+8×5+4+4+8 = **216 字节**；8KB 页约放 37 行（含 4B/槽）。

## 3. 索引规划（对应大赛题3 与题4）

| 索引 | 表 | 列 | 唯一 | 服务的查询 |
|---|---|---|---|---|
| `pk_orders` | orders | oid | 是 | 订单详情、状态轮询（PK） |
| `idx_orders_pid_time` | orders | (pid, created_at) | 否 | 乘客近 30 天订单、我的订单列表 |
| `idx_orders_state_time` | orders | (state, created_at) | 否 | 区域待接单列表（先按状态过滤再按时间排序） |
| `idx_orders_did_time` | orders | (did, created_at) | 否 | 司机当日流水、司机工作量统计 |
| `uk_accounts_login` | accounts | login_name | 是 | 登录 |
| `uk_passengers_phone` | passengers | phone | 是 | 手机号唯一 |
| `uk_drivers_phone` | drivers | phone | 是 | 手机号唯一 |
| `uk_vehicles_plate` | vehicles | plate | 是 | 车牌唯一 |
| `idx_vehicles_did` | vehicles | did | 否 | 司机名下车辆 |
| `idx_events_oid_time` | order_events | (oid, at) | 否 | 订单时间轴回放 |
| `uk_reviews_oid` | reviews | oid | 是 | 一单一评 |

**性能对比点（B1/B2）**：`SELECT ... FROM orders WHERE pid=? AND created_at >= ?` 无索引走 SeqScan（约 20 万行），加 `idx_orders_pid_time` 后走范围扫描。数字写进 `docs/性能报告.md`。

## 4. 需求 → 表/命令 映射

| 需求 | 主表 | 业务命令 | 关键约束 |
|---|---|---|---|
| 1 乘客下单 | orders、addresses | ORDER_CREATE | 状态必须初始为 1 待接单；常用地址复用 |
| 2 派单与接单 | drivers、vehicles、orders | DISPATCH / ORDER_ACCEPT / ORDER_REJECT | 候选司机须 online=1、audit_state=1、车辆 op_state=1、车型匹配 |
| 3 行程执行 | orders、order_events | TRIP_ARRIVE / TRIP_START / TRIP_FINISH | 只有 4 行程中才允许 finish |
| 4 状态追踪 | orders、order_events | 状态查询 | 每次流转写一条 event + 对应时间戳 |
| 5 计价 | price_rules、orders | PRICE_CALC / TRIP_FINISH | 整数分运算，见 `CalcFare` |
| 6 司机车辆管理 | drivers、vehicles | DRIVER_TOGGLE / ADMIN_QUERY | 上下线、运营状态互斥关系 |
| 7 账号角色 | accounts | LOGIN | 3 角色权限矩阵见 `docs/协议v0.md` §5 |
| 选做 评价 | reviews | ADMIN_QUERY | 一单一评由唯一索引保证 |

## 5. 压测数据规模（对标大赛 TPC-C 的"固定规模"思路）

| 实体 | 行数 | 说明 |
|---|---|---|
| accounts / passengers | 50,000 | 乘客为主 |
| drivers / vehicles | 2,000 | 每司机 1 车 |
| orders | 200,000 | 历史 + 当日混合 |
| order_events | 600,000 | 平均 3 次流转/单 |
| reviews | 20,000 | 10% 评价率 |

堆文件估算：orders 200k × 216B ≈ 43MB，事件 600k × 36B ≈ 22MB，合计 < 100MB，单机磁盘完全够；压测时全部可进 256 页缓冲池的 LRU（这也是要观察命中率的原因——池子只有 2MB，必然频繁换页）。
